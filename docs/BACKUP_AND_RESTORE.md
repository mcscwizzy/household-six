# Backup and restore

Create timestamped snapshots in the persistent backup volume with `docker compose run --rm household-six python3 /app/scripts/backup.py` (or `docker-compose` on a host using Compose v1). Schedule it with DSM Task Scheduler. Copy those files to a second protected NAS share or other independent backup target. A Docker volume survives app-container replacement, but a second copy is still needed for NAS failure.

The script uses SQLite's online backup API, then archives the snapshot. Verify an archive periodically by restoring to a new empty data volume: stop the app, set `DATA_PATH=household-six-restore-data`, run `docker compose run --rm household-six python3 /app/scripts/restore.py /app/backups/<archive>.tar.gz`, verify the restored DB, update `.env` with that `DATA_PATH`, then start the app. The script checks the archive's single expected member and runs `PRAGMA integrity_check`; it refuses to overwrite an existing database. A disposable Compose run for this continuation restored synthetic data to a separate volume and verified SQLite integrity plus owner and completed-task records.

The current branch has no uploaded-file storage, so the database contains the implemented household data set. When attachments or media are added, database and file snapshots must be coordinated consistently before release. Backups contain password hashes and personal family records; encrypt and restrict them. The restore rehearsal was synthetic and local; it is not physical NAS acceptance evidence.
